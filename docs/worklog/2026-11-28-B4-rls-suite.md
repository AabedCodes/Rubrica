## What was done

- `tests/authz/test_rls.py`: 36 cases against a real PostgreSQL, connecting as each runtime role through `backend.db.session()`.
  - **Catalog:** all 24 data tables have RLS enabled and forced. No runtime role is superuser, BYPASSRLS, CREATEROLE or CREATEDB. No role holds UPDATE, DELETE or TRUNCATE on `audit_log`.
  - **`rubrica_mcp` as a student:**
    - with no `WHERE` clause, `proposed_grades` returns only her own released grade;
    - `answer_keys` returns 0 rows, and the key text isn't findable;
    - no other course's assignments or blog chunks;
    - `UPDATE proposed_grades SET status='released'` is denied (42501).
  - **`rubrica_grading` for run 1:** sees only run 1's submissions and key; blog tables are denied.
  - **`rubrica_ingest`:** denied on `submissions`, `proposed_grades` and `answer_keys`.
  - **Every role:** `UPDATE` and `DELETE` on `audit_log` are denied.
  - **Fail closed:** 9 role/table pairs with no RLS context return 0 rows.
- `tests/verification/test_T23_missing_filter.py`: the plan's T-23 case in the `@verification` format.
- **FINDING-B4-01**, recorded as 2 strict-xfail tests and in `docs/threat-model/changes.md`. Issue opened for D.

## How

The seed has two courses:
- alice and bob in course 1, carol in course 2;
- grades in every state: alice released, bob released, alice pending on a second assignment, carol released;
- one answer key;
- blog chunks in both courses.

Queries deliberately omit the ownership filter, because the claim under test is "the database holds even when the code forgets". Permission failures are checked by SQLSTATE `42501`, not just "some error".

## Decisions

| Decision | Alternatives considered | Why |
|---|---|---|
| Query tables directly instead of D's service functions | reuse D1's tests | D1 tests D's functions; B4 has to show the *database* holds when code is wrong, which only direct queries show |
| A gap found by the suite is a strict xfail plus an issue, not a deleted or weakened assertion | fail the build; drop the test | keeps CI usable for everyone while recording the gap; strict means the test fails the moment D fixes it, so the marker can't outlive the bug |
| Separate from D1's file | add cases to `test_d1_database.py` | D owns that file; B owns the cross-cutting suite (plan §B4) |
